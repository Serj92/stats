### `6a8e1e93` (#3368) — один конфликт, разрешён в нашу API

`readers.swift` у нас был байт-в-байт апстримный → лёг чисто. `main.swift` тоже. Конфликт один — вставка секции адаптера в `renderUsage()`.

- **Что хотел апстрим:** перестать хардкодить индекс `3` и считать позицию от фактического места секции батареи (для этого они завели `batterySection`).
- **Что у нас:** двухколоночный каркас со своим реестром секций (`insertSection`/`layoutColumns`), а не голый `insertArrangedSubview`/`recalculateHeight`.
- **Разрешено:** оставлен наш API, но взята их идея — индекс выводится из позиции секции батареи. Под это в `Kit/module/popup.swift` добавлен симметричный остальным мутаторам аксессор `sectionIndex(of:) -> Int?`; вызов стал `self.batterySection.flatMap({ self.sectionIndex(of: $0) }).map({ $0 + 1 }) ?? 3`.

**Смысл самой фичи** (пригодится, если попап будем ещё двигать): строки Power/Current/Voltage перестали быть общими — раньше одни и те же три поля показывали то батарею, то адаптер в зависимости от источника питания. Теперь они переехали в секцию батареи и **всегда** показывают батарею, а секция адаптера получила свои три строки, с тултипами на charging current/voltage. В ридере `adapterVoltage`/`chargingCurrent`/`chargingVoltage` теперь явно обнуляются и заполняются только при `!isBatteryPowered` (раньше при работе от батареи там висели стухшие значения от адаптера), а `timeToEmpty`/`timeToCharge` пишутся всегда, а не только при наличии ключа.

**Высоты трогать не пришлось:** `layoutColumns()` меряет секции через `naturalHeight()`, так что перенос трёх строк из одной секции в другую каркас перебалансировал сам.

## 2026-08-02 — v3.0.9 → v3.0.10 (частичный синк, версию не бампали)

Апстрим выпустил **v3.0.10**. Дельта `9a750c7f..64a34fa3` — 4 коммита, но три фикса из релиз-нотов (#3410/#3439/#3476) **уже наши** с 29 июля. Реально нового два: фикс Net-ридера и редизайн Combined view. Взяли первый, второй **отложен** (см. ниже).

**#3499 — ради этого и синкались.** В `Kit/helpers.swift` появился хелпер `process(path:arguments:environment:timeout:)`: две `DispatchGroup` (выход процесса + дренаж обоих пайпов), по таймауту `terminate()`, если не помер за 2с — `SIGKILL`, чтение stdout вынесено в фоновую очередь (иначе `readDataToEndOfFile()` блокируется навечно). Через него переведены оба вызова `nettop` (`UsageReader.readProcessBandwidth`, `ProcessReader.read`, таймаут 5с) и `system_profiler SPAirPortDataType` — последний потерял свою самодельную таймаут-обвязку (`Modules/Net/readers.swift` −111 строк). По классу это продолжение нашей же линии фиксов в Net (гонка от 15.07, `requestRead()`).

> **Конфликт был один, в `ProcessReader.read()`.** Наш форк держит там reentrancy-lock (`lock`/`reading` + `defer`), апстрим ровно в этом месте вырезал inline-`Process`. Разрешено вручную: наш блок с локом остаётся, тело заменено на их `guard let output = process(...)`. Второй и третий хунки (`readProcessBandwidth`, `systemProfilerAirport`) и весь `Kit/helpers.swift` легли чисто.

**Тамильский** взят просто чтобы не копить дельту: авто-мердж pbxproj прошёл (3 хунка — `PBXFileReference`, `knownRegions`, вариантная группа), кода не касается. Наши форковые строки в `ta.lproj` отсутствуют → у тамильской локали они упадут в английский фолбэк, для личного форка неважно.

### Отложено: `43e4a943` «redesigned Combined view»

Апстрим переделал комбинированный вид **в свою сторону**, и это лобовое пересечение с текущей незавершённой работой форка (двухколоночная сетка + карточка fan-control).

Что там сделано:
- `Constants.Popup.portalHeight` (120) **удалён**; `Portal_p` получил `var height`, каждый модуль объявляет свою: Battery 70, GPU 70, RAM 80, Net 90, Clock 110, CPU 120, Disk 120 (плюс 20 на хедер и spacing).

**РЕШЕНО 03.08: редизайн не берём, вариант (б).** Гибрид (вариант «в» — их порталы + наша сетка) был реально собран в скрэтч-worktree и компилировался (`BUILD SUCCEEDED`), но его забраковали по внешнему виду: раз у порталов теперь разные высоты (70…120), а ряд в сетке всегда по самой высокой ячейке, в двух колонках появляются пустые провалы — рядом с CPU дырка ~50pt (GPU), рядом с Disk ~40pt (RAM). У апстрима в одну колонку этой проблемы нет, у нас в сетке она неустранима без растягивания портала или сортировки ячеек по высоте (ломает порядок модулей). ### Часть 3 — системная сериализация `read()` (тем же днём, билд 822)

Развитие фикса краша из Части 1. `readIfIdle()`-guard прикрывал только **плановый** путь (`start()` + репитер), а колбэки настроек во всех модулях зовут `read()` **напрямую** с фоновой очереди — мимо guard'а. Аудит показал тот же класс гонки, что ронял Net, ещё в двух ридерах (у пользователя оба модуля активны):
- **CPU `LoadReader`** (`readers.swift:52`) — `CPUUsageLock` прикрывает только чтение `prevCpuInfo`; `vm_deallocate` + переприсваивание указателя идут **вне лока** → наложение двух `read()` = use-after-free на сырой mach-памяти.
- **Disk `CapacityReader`** — `smartCache`/`purgableSpace`/`smartTotals` (обычные `Dictionary`) + `self.list` мутируются без лока.
- RAM `ProcessReader` — буфера между вызовами нет, безопасен.

**Фикс.** Публичный `Reader.requestRead()` — диспатчит на фоновую очередь и идёт через `readIfIdle()`. Все **19** прямых `read()` в `Modules/*/main.swift` переведены на него (заодно убраны ручные `DispatchQueue.global.async`-обёртки). Теперь `read()` любого ридера не может пересечься сам с собой при любом входе (план + настройки) → CPU-UAF и Disk-гонка закрыты без пер-ридерных локов. У CPU `LoadReader`/Disk `CapacityReader` своих `self.read()` нет (проверено grep'ом), так что покрытие полное. Компромисс: refresh по настройке во время идущего чтения отбрасывается, подхватится следующим тиком (≤ интервал).

## 2026-06-28 — локальная правка логгера + ре-деплой Release (RAM-гигиена)

Не синк — локальная оптимизация по запросу «выкинуть debug из шипнутой сборки».

**`debug()` → no-op в Release.** `Kit/plugins/Logger.swift`: сигнатура переведена на `@autoclosure () -> String`, тело обёрнуто в `#if DEBUG`. Раньше каждый из **60 вызовов** `debug()` всегда строил префикс (с **новым `DateFormatter` на каждый вызов**!) и писал в stderr — даже в Release, фильтра по уровню в `NextLog` нет. Теперь в Release строка-сообщение **не вычисляется вообще**. `info()`/`error()` не трогали (низкочастотные, полезны для диагностики).

⚠️ **Новое локальное расхождение с upstream** — при следующем rebase должно пережить merge (`Logger.swift` апстрим трогает редко). Закоммичено отдельным `local:`-коммитом перед rebase на v3.0.5 (см. запись 2026-06-29 ниже).

**`get-task-allow` — это НЕ признак Debug-сборки.** По ходу выяснилось: `com.apple.security.get-task-allow=1` сидит и в Release тоже — он инжектится при подписи **dev-сертификатом «Apple Development»**, а не конфигурацией Debug. Убирается только Distribution-подписью (Developer ID, у нас нет). На RAM/работу не влияет — лишь разрешает присоединять отладчик. Раньше это ошибочно принималось за «в /Applications лежит Debug». Вписано в [SIGNING.md](SIGNING.md).

**Ре-деплой.** Пересобрали v3.0.4 (804) в Release (рецепт из SIGNING.md без изменений), sanity-check зелёный (3 OU = `T5V6W6793A`), `ditto` в `/Applications` с бэкапом `/tmp/Stats-backup.app`. SHA-256 установленного бинаря == собранного. Исполняемый файл ~16 КБ меньше прежнего; на установившуюся RAM правка почти не влияет (реальные рычаги — число модулей, длина истории графиков, частота опроса).

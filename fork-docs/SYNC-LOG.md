## 2026-10-28 — перф-проход: DNS в Net и подписка ANE в GPU (билд 852)

Не синк — вопрос «что ещё можно облегчить» по живому 851.

**Метод — важно на будущее.** `sample` считает время на часах, включая ожидание. Для очередей с фоновым QoS (а наши ридеры такие) это сильно завышает долю: `getDetails` в `sample` — 479 мс за 60 с, а по Time Profiler реального CPU — 165 мс за 90 с. Тот же код в отдельном процессе: 7.5 мс обычным, ~35 мс под `taskpolicy -b`. Атрибуцию CPU делать Time Profiler'ом (только сэмплы `Running`):
`xcrun xctrace record --template 'Time Profiler' --attach <pid> --time-limit 90s --output X.trace` → `xctrace export --xpath '…table[@schema="time-profile"]'` → разбор по кадрам `XReader.read()`. Скрипты не в репо.

**Раскладка 851 в простое, окна закрыты** (CPU за 90 с, всего 1299 мс ≈ 1.4 % ядра): GPU `InfoReader` 19 % (из них ANE 11 %, FPS 4 %), главный поток `CA::Transaction::commit` 18 %, ядро без стека 16 %, Net `getDetails` 13 %, Net `read` 6 %, Disk 5 %, CPU/RAM ~1 %. Свежий процесс первые 2–3 мин тратит заметно больше — A/B общего CPU с короткой паузой после запуска это искажает.

**Правки (`590220fb`), поведение то же:**
- **Net `getDetails()`**: служба → BSD-имя теперь одним `SCDynamicStoreCopyMultiple` по `Setup:/Network/Service/[^/]+/Interface` (`DeviceName`), вместо `SCNetworkServiceCopyAll` + `SCNetworkServiceGetInterface` (строил полный объект интерфейса с поиском bridge и обходом IORegistry для каждой службы). Сверено по всем службам машины: соответствие совпало, кроме одной службы из другой локации, которой нет в `Setup:` — DNS-состояния у неё нет ни там, ни там. Бенч: 5.5 → 0.1 мс, DNS тот же. Возможное расхождение — PPP/PPPoE-службы (их `DeviceName` — нижний интерфейс); здесь таких нет.
- **GPU `setupANE()`**: подписка IOReport сужена до каналов `ANE*` (здесь 1 из 196 в группе `Energy Model`). Бенч: счётчик ANE тот же, выборка 1.25 → 0.83 мс (под фоновым QoS 3.0 → 1.5).

**Замер** (Time Profiler, 90 с, CPU в изменённых местах): `getDetails` 165 → **63 мс**, `readANEPower` 141 → **94 мс** — вместе −150 мс / 90 с, ≈ 11 % CPU Stats. Итог процесса по одиночным прогонам 1299 → 1251 мс — в пределах шума, общим CPU выигрыш не подтверждён и не опровергнут. Длинный A/B (6 раундов, ~35 мин) отменён как несоразмерный. ### Производительность без открытых окон (условие синка)

Почему дёшево по коду: `ProcessReader` — `popup`+`preview`, в `startReaders()` он `locked`, базовый `start()` делает одно `readIfIdle()`, а их `read()` упирается в `guard self.active` и выходит. ### Регрессия памяти и фикс (`d0555093`)

После первого деплоя 850 RSS был ~390 МБ против ~257 у 849 (A/B в одном окне, два раунда). `footprint`: 850 — 260 / 248 МБ, 849 — 189 МБ; весь прирост в регионе **CoreAnimation**: 57–61 МБ против 0.9 МБ, это 15 регионов по 4 МБ (= 1024×1024×4). `git bisect run` по Debug-сборкам (порог CoreAnimation ≥ 20 МБ через 120 с после старта, compat RAM накладывался на лету) указал на `3bca6435` (`5808bf92`).

Механизм: превью заполняют строки процессов один раз при старте, ещё не будучи показанными (`|| !self.initializedProcesses` в `processCallback`), а layer-backed `NSImageView` в каждой строке растеризует в слой 1024-px представление иконки приложения. Попапы так не делали — до открытия не рисуются. Проверка гипотезы: с `Constants.defaultProcessIcon` вместо иконок приложений CoreAnimation 61 МБ → 4.6 МБ (один 4-МБ регион — сама дефолтная иконка).

Фикс: `ProcessIconCache` хранит drawing-handler `NSImage` 18 pt (самая крупная иконка строки), который растеризуется в размер показа. Debug через 120 с: CoreAnimation 864 КБ, 4-МБ регионов нет. Задеплоенный Release через 150 с: footprint **196 МБ**, CoreAnimation 736 КБ (849 — 189 МБ, одиночные замеры). Иконки в превью/попапах после фикса **глазами не смотрелись**.

**Грабли на будущее:** после синка, который трогает UI, сравнивать `footprint` + `vmmap --summary` с прошлой сборкой, а не только RSS. Скрипт bisect (`git bisect run` + Debug-сборка + замер `vmmap`) работает за ~5 шагов по 3–4 мин; ловушка — `git bisect start` не принимает `-q` (молча считает его ревизией).

> **Поправка к тому, что тут сначала было записано.** Первая редакция этой записи утверждала, что апстрим утащил «два дефекта»: `guard disk != kIOReturnSuccess` вместо `!= 0` и утечку io_object-хэндла. **Проверено — оба утверждения неверны.**
> - `kIOReturnSuccess` — это `Int32(0)`, а `io_service_t` — `UInt32`; Swift сравнивает разные целочисленные типы штатно, так что `disk != kIOReturnSuccess` численно равно `disk != 0`. Код путает типы и читается плохо, но работает правильно.
> - Утечки нет. `defer { IOObjectRelease(disk) }` в Swift захватывает **переменную**, а не значение, и на выходе освобождает актуальный хэндл; внутри цикла старый освобождается явно перед переприсваиванием. Ранний `return nil` тоже покрыт этим же `defer`.
>

## 2026-06-28 — локальная правка логгера + ре-деплой Release (RAM-гигиена)

Не синк — локальная оптимизация по запросу «выкинуть debug из шипнутой сборки».

**`debug()` → no-op в Release.** `Kit/plugins/Logger.swift`: сигнатура переведена на `@autoclosure () -> String`, тело обёрнуто в `#if DEBUG`. Раньше каждый из **60 вызовов** `debug()` всегда строил префикс (с **новым `DateFormatter` на каждый вызов**!) и писал в stderr — даже в Release, фильтра по уровню в `NextLog` нет. Теперь в Release строка-сообщение **не вычисляется вообще**. `info()`/`error()` не трогали (низкочастотные, полезны для диагностики).

⚠️ **Новое локальное расхождение с upstream** — при следующем rebase должно пережить merge (`Logger.swift` апстрим трогает редко). Закоммичено отдельным `local:`-коммитом перед rebase на v3.0.5 (см. запись 2026-06-29 ниже).

**`get-task-allow` — это НЕ признак Debug-сборки.** По ходу выяснилось: `com.apple.security.get-task-allow=1` сидит и в Release тоже — он инжектится при подписи **dev-сертификатом «Apple Development»**, а не конфигурацией Debug. Убирается только Distribution-подписью (Developer ID, у нас нет). На RAM/работу не влияет — лишь разрешает присоединять отладчик. Раньше это ошибочно принималось за «в /Applications лежит Debug». Вписано в [SIGNING.md](SIGNING.md).

**Ре-деплой.** Пересобрали v3.0.4 (804) в Release (рецепт из SIGNING.md без изменений), sanity-check зелёный (3 OU = `T5V6W6793A`), `ditto` в `/Applications` с бэкапом `/tmp/Stats-backup.app`. SHA-256 установленного бинаря == собранного. Исполняемый файл ~16 КБ меньше прежнего; на установившуюся RAM правка почти не влияет (реальные рычаги — число модулей, длина истории графиков, частота опроса).

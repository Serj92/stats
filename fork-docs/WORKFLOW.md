# Workflow

## Как всё устроено сейчас

Одна живая ветка — **`local/build`**. На ней лежит апстримный код плюс наши коммиты, с неё собирается и деплоится приложение, она же зеркалится в `origin` как бэкап.

```
upstream/master ──┐
                  │  cherry-pick отдельных коммитов
                  ▼
             local/build   ← ЕДИНСТВЕННАЯ рабочая ветка
                  │  git push origin local/build (fast-forward, бэкап)
                  ▼
          origin/local/build
```

Перед каждым синком снимается бэкап-ветка `backup/local-build-pre-<версия>` — она и есть кнопка «отменить всё».

### Ветки-архивы (в работе не участвуют)

| Ветка | База | Что там |
|---|---|---|
| `master` | v2.12.15 | когда-то был «чистый синхрон с апстримом» |
| `feat/personal-tweaks` | v2.12.14 | 3 фича-коммита + первая версия этой доки |
| `feat/cpu-cores-color`, `feat/ram-pressure-bar`, `feat/widget-split-io` | v2.12.14 | те же фичи по отдельности, под upstream-PR |

**Почему они мёртвые.** Схема с чистыми фича-ветками существовала ради PR'ов в апстрим. `exelban/stats` — closed-contribution: неспрошенные PR закрывают не читая (закрыли все три наших), доезжают только issue. 2026-08-09 решено не отправлять апстриму ничего — вместе с этим отпал и смысл держать фичи отдельно от сборочной ветки. Все три фичи живут в `local/build` и поддерживаются там.

Ветки оставлены как исторические снапшоты; актуализировать их (14 релизов отставания) незачем. Если когда-нибудь понадобится отдать код наружу — проще заново снять патч с `local/build`, чем реанимировать v2.12.14.

## Ежедневная работа

```bash
git checkout local/build
# ... правишь, собираешь, тестируешь ...
git add <файлы>
git commit -m "feat: краткое описание"
```

Никуда переносить коммит не надо, `local/build` — конечная. Порядок коммитов на ветке значения не имеет: правки под старый Xcode лежат отдельными коммитами там, где их сделали, и «последним» ничего быть не обязано (см. [XCODE-COMPAT.md](XCODE-COMPAT.md)).

Новые строки интерфейса — сразу EN + RU + UK в `*.lproj/Localizable.strings`. Проверка: `python3 Kit/scripts/i18n.py` (без аргументов — `check`), добор пропусков — `python3 Kit/scripts/i18n.py fix`.

## Синхронизация с upstream

### Шаг 1 — посмотреть, что там

```bash
git fetch --all --tags
git log --oneline $(git merge-base local/build upstream/master)..upstream/master   # всё, чего у нас нет
git log --oneline <последний-взятый-коммит>..upstream/master                       # только новая дельта
```

`merge-base` показывает точку последнего **ребейза** (сейчас `2fff0dfb`, v3.0.5) — с тех пор апстрим приходит cherry-pick'ами, поэтому «чего у нас нет» по merge-base включает и то, что уже взято. Реальная дельта считается от последнего взятого апстримного коммита; он назван в верхней записи [SYNC-LOG.md](SYNC-LOG.md).

Дальше по каждому коммиту решается «брать или нет». Практика: **берётся почти всё, включая бесполезное для этой машины.** Довод — файл, совпадающий с апстримом байт-в-байт, не конфликтует на следующем синке; отказ от однострочника «нам не надо» окупается отрицательно. Смотреть, насколько файл уже разошёлся с апстримом:

```bash
git diff --shortstat <последний-взятый-коммит> HEAD -- <файл>
```

Не берётся: то, что меняет поведение против наших решений (см. записи про Preset selector, дефолт телеметрии), и то, что тянет за собой большую i18n-поверхность без пользы.

### Шаг 2 — бэкап и пики

```bash
git branch backup/local-build-pre-<версия> local/build
git cherry-pick <sha>            # по одному, в апстримном порядке
```

Коммит-сообщения апстрима сохраняются как есть — так `git log --oneline` сопоставляется с апстримным. Если взяли не весь коммит, **это пишется в тело коммита** (пример — `dfaf9375`), а не только в SYNC-LOG.

Когда конфликт выглядит как «удалили 250 строк тут, добавили похожие 300 там» — резолвить по ханкам бесполезно. Взять апстримный файл целиком и переналожить свой дифф:

```bash
git checkout --theirs <файл>
git diff <последний-взятый-коммит>..HEAD -- <файл> > /tmp/ours.patch
git apply --reject /tmp/ours.patch
```

После `--reject` читать не только `.rej`, но и **куда сели «успешные» ханки**: при сдвигах они попадают в соседний класс с тем же именем метода (ловилось на `SMARTReader` в синке v3.0.14 — спасло только совпадение имён и компилятор).

### Шаг 3 — версия

Бамп — свой коммит `local: bump to X.Y.Z (NNN) after vX.Y.Z upstream sync`, в трёх местах:

```bash
sed -i '' 's/MARKETING_VERSION = <старая>;/MARKETING_VERSION = <новая>;/' Stats.xcodeproj/project.pbxproj
/usr/libexec/PlistBuddy -c "Set :CFBundleVersion <NNN>" "Stats/Supporting Files/Info.plist"
/usr/libexec/PlistBuddy -c "Set :CFBundleShortVersionString <новая>" "Widgets/Supporting Files/Info.plist"
/usr/libexec/PlistBuddy -c "Set :CFBundleVersion <NNN>" "Widgets/Supporting Files/Info.plist"
git diff --stat    # должно быть ровно 5 строк в 3 файлах, PlistBuddy иногда переформатирует
```

`CFBundleVersion` у нас **своя нумерация** и она впереди апстримной (разошлись на 3.0.9) — брать следующее число от нашего, не от апстримного.

> **⚠️ Где стоит тег — проверять каждый раз.** На `v3.0.1` тег указывал на коммит, где `MARKETING_VERSION` ещё старая (бамп был следующим коммитом) — сборка с тега показывала 3.0.0. На `v3.0.4`, `v3.0.12`, `v3.0.14`, `v3.0.15` бамп уже **внутри** тега. Проверка: `git show <тег>:Stats.xcodeproj/project.pbxproj | grep -m1 "MARKETING_VERSION = 3"`.

### Шаг 4 — собрать и проверить

Компилируемость под старый Xcode (без подписи, быстро):

```bash
xcodebuild -project Stats.xcodeproj -scheme Stats -configuration Debug \
  -derivedDataPath <любой-каталог> \
  build CODE_SIGN_IDENTITY="-" CODE_SIGNING_REQUIRED=NO CODE_SIGNING_ALLOWED=NO
```

Вывод `xcodebuild` огромный — грепать `-E "^\*\* BUILD|error:"`, иначе «BUILD» матчится о `export BUILD_DIR=…`.

Если апстрим завёл конструкцию, которую Xcode 16.0 не переваривает — новый точечный коммит-downgrade, см. [XCODE-COMPAT.md](XCODE-COMPAT.md).

Release-сборка, подпись, sanity-check и деплой в `/Applications` — [SIGNING.md](SIGNING.md).

### Шаг 5 — записать

Запись в [SYNC-LOG.md](SYNC-LOG.md) сверху: таблица «апстримный sha → наш sha → что → как лёг», отдельными разделами — конфликты и чем именно их резолвили, что не взято и почему, итог сборки и деплоя. Смысл записи — чтобы следующий синк не наступил на те же грабли; поэтому граблей в ней должно быть больше, чем перечисления фич.

### Синк руками Claude — без `git rebase -i`

Интерактивный rebase в Claude Code недоступен. Вложить правку в не-HEAD коммит можно через detached-amend:

```bash
git checkout --detach <commit>
# ... правим ...
git commit --amend
git rebase --onto HEAD <commit> <старый-HEAD>
git branch -f local/build HEAD && git switch local/build
```

На практике при cherry-pick-схеме это почти не нужно: правка кладётся новым коммитом сверху.

## Правила-предохранители

1. **`local/build` уходит только в `origin` и никогда в upstream.** На ветке коммиты-downgrade «DO NOT MERGE» и своя signing-идентичность — этому не место в чужом репозитории. Пуш теперь обычный fast-forward (`git push origin local/build`): историю мы не переписываем, `--force` не нужен и без явной причины не применяется. Снять ветку с origin, если понадобится: `git push origin --delete local/build`.

2. **Бэкап-ветка перед каждым синком, до первого cherry-pick.** `backup/local-build-pre-<версия>`. Чистить их можно только те, чей коммит достижим из `local/build` (`git merge-base --is-ancestor <ветка> local/build`) — остальные держат снапшоты, которых больше нигде нет.

3. **Апстримные коммит-сообщения не переписываются**, кроме случая частичного взятия — тогда расхождение пишется в тело коммита.

4. **Не брать апстримную правку, которая молча меняет поведение в нашу сторону хуже** — даже ценой байт-в-байт совпадения файла. Вместо этого взять остальную часть коммита и записать отказ.

5. **Доку обновлять при структурных изменениях.** Эта дока уже один раз разошлась с реальностью на три релиза (описывала схему `master → feat/personal-tweaks → local/build` с ребейзами, когда работа давно шла cherry-pick'ами на `local/build`) — так что если меняешь схему, правь здесь сразу, а не «потом».
